很多项目里的 `docs/` 文件夹，最后都会变成一个奇怪的地方。

里面可能有一张半年前的架构图、一份已经失效的接口设计、几篇不知道该不该相信的开发记录，以及一个永远没有写完的 TODO。

这些文件单独看都有点用，放在一起却很难说明项目现在到底是什么样子。

所以很多时候，我们干脆不看文档，直接看代码。

代码至少不会骗人。它能运行成什么样，项目就是什么样。

但当项目越来越大，尤其当 Agent 开始一次修改十几个、几十个文件以后，直接通过代码理解整个项目，也开始变成一件成本很高的事情。

代码里有太多细节。

你只是想知道一个模块应该依赖谁，却需要沿着 Import、类型、构造函数和方法调用一路追下去。最后确实得到了答案，但脑子里也顺便装进了一堆当前根本不需要关心的实现。

这时，一个好的 `docs/` 文件夹可以承担另一种作用：

> 它不是代码的说明，而是代码的映射。

代码保留完整实现，文档保留系统的形状。

## 代码本来就存在拓扑

一个项目并不是一堆互不相关的文件。

文件之间有 Import，模块之间有调用，接口连接前端和后端，事件连接生产者和消费者，数据从一个组件流向另一个组件。

代码天然就是一张图。

文件可以看作节点，引用、调用和依赖则是边。

只不过这张图被藏在了大量实现细节中。

例如，一个实际项目可能是这样的：

```text
HTTP Route
    ↓
Service
    ├──→ Domain
    └──→ Repository
              ↓
           Database
```

代码中当然能够找到这些关系，但它们可能分散在很多文件里。

文档可以把这些关系重新映射出来，只留下当前需要关心的部分。

它不需要解释每个函数怎样实现，也不需要跟着每一次变量重命名同步修改。它只需要说明一些更稳定的事情：

* 哪个模块负责什么；
* 哪个模块依赖哪个模块；
* 数据由谁拥有；
* 状态从哪里产生；
* 哪一层可以访问数据库；
* 哪些边界不能跨越；
* 哪份内容是事实源；
* 哪些功能已经完成；
* 哪些只是预留接口。

代码是一张包含所有细节的地图。

文档是一张可以缩放的地图。

## 文档文件本身也能组成拓扑

文档系统不一定只是一个目录树。

每一份 Markdown 文件都可以看成一个节点。

文件路径是节点的索引，文档中的链接和引用则是节点之间的边。

比如：

```text
docs/
├── README.md
├── architecture/
│   ├── overview.md
│   ├── combat.md
│   └── memory.md
├── design/
│   ├── game-loop.md
│   └── skill-system.md
├── decisions/
│   ├── 001-server-authoritative.md
│   └── 002-memory-boundary.md
└── tasks/
    ├── active/
    └── completed/
```

按目录查看时，它是一棵树。

`architecture/`、`design/`、`decisions/` 和 `tasks/` 是不同分支，文件根据用途被分到不同路径。

但目录树只是这套文档文件拓扑的一种视图。

例如，`architecture/combat.md` 可能引用：

```text
architecture/overview.md
design/skill-system.md
decisions/001-server-authoritative.md
tasks/active/combat-playback.md
```

于是，这几个文件之间又形成了一张有向图：

```text
README.md
    ↓
architecture/overview.md
    ↓
architecture/combat.md
    ├──→ design/skill-system.md
    ├──→ decisions/001-server-authoritative.md
    └──→ tasks/active/combat-playback.md
```

这里的有向图，指的仍然是**文档文件之间的拓扑**。

一份文件指向另一份文件，意味着：

* 阅读这份文档前，应该先了解另一份；
* 当前架构依赖某项设计；
* 某个实现遵守某项历史决策；
* 一个任务需要修改或验证某个模块；
* 一份新文档替代了一份旧文档；
* 一个阶段报告对应一次具体开发。

同一套文件，可以同时被看作列表、目录树和有向图。

列表适合表达顺序：

```text
1. 当前正在做什么
2. 下一步准备做什么
3. 哪些内容等待确认
4. 哪些内容暂时不做
```

目录树适合表达分类和归属：

```text
architecture/
design/
reference/
workflow/
```

有向图适合表达跨目录关系。

一个文件在磁盘上只能放在一个路径里，但它可以和很多其他文件产生连接。

所以，文件路径不仅是存储位置。

它也是稳定索引。

而 Markdown 链接，就是文档拓扑中的边。

## 文档是镜像，但不应该复读代码

把文档称为代码的镜像，很容易产生一个误解：

是不是代码里有什么，文档里就要重新写一遍？

当然不是。

如果代码中有一个 `CombatService.startBattle()`，文档里又写：

> `CombatService` 中存在一个 `startBattle` 方法，用于开始战斗。

这种文档几乎没有意义。

函数改名以后，它立刻过期。即使没有改名，它提供的信息也不比直接搜索代码更多。

好的文档镜像，不映射代码的每一个像素。

它映射代码的轮廓。

例如，代码中可能有几十个战斗相关类，但文档只需要保留：

```text
战斗入口
    ↓
战前快照
    ↓
纯函数模拟
    ↓
按模式结算
    ↓
持久化结果
    ↓
前端播放动作序列
```

这张图不关心某个方法叫什么，却能说明：

* 战斗结果由服务端产生；
* 前端只负责播放；
* 模拟过程不应该直接读取数据库；
* 不同战斗模式的差异应该放在结算阶段；
* 战斗开始后使用不可变快照。

这些规则比具体函数名稳定得多。

实现可以从一个类拆成五个类，也可以从同步改成异步，只要模块责任没有改变，文档拓扑就不需要被彻底重写。

反过来，如果责任发生变化，即使代码还能运行，文档也应该更新。

## 不看所有代码以后，反而更需要文档

在 Agent 出现以前，开发者通常通过亲手写代码和阅读代码维持对项目的理解。

现在，Agent 可以自己搜索仓库、修改文件、运行测试、分析报错，再继续修复。

一次任务可能产生大量代码，而开发者不会再逐行确认全部实现。

这并不一定是坏事。

很多语法、样板代码、数据转换和测试补充，本来就不值得人类投入同样多的注意力。

但当我们不再关注所有代码细节后，就必须在更高一层掌握项目。

至少要知道：

* 项目目前有哪些模块；
* 模块之间怎样连接；
* 哪个模块拥有某项状态；
* 一次修改影响了哪些节点；
* 哪条边界正在被突破；
* 哪些内容还没有真正完成；
* 当前实现未来准备怎样扩展。

`docs/` 就是用来保存这层理解的。

它让你不需要记住所有文件，却仍然知道系统怎样组成。

你不需要记住限流器里具体怎样计算 Token，只需要知道：

```text
实时连接
├── 握手限流
├── 账号连接限制
├── 命令成本限制
└── 重连不能重置额度
```

你不需要记得检索系统里每一个评分函数，只需要知道：

```text
查询
    ↓
多路召回
    ↓
候选合并
    ↓
证据筛选
    ↓
文件读取
    ↓
回答或拒答
```

文档不是帮助你了解得更细。

它是帮助你在不进入全部细节的情况下，仍然掌握整体。

## 实时更新的文档，才能称为映射

如果代码已经改变，文档仍然停留在三个月前，那它就不是镜像了。

它更像一张旧地图。

路还画在上面，但桥已经拆了。你按照它走到河边，才发现前面根本过不去。

所以真正有用的文档不能等项目完成后再整理。

它应该和代码一起变化。

新增一个模块，就把模块节点加入文档拓扑。

改变依赖关系，就修改文件之间的引用。

某个临时占位被补齐，就从待办或占位文档中移除。

一项方案被放弃，可以把它移到历史目录，并让新文档明确指向替代方案。

文档中的状态应该始终尽量接近代码中的状态：

```text
已完成什么
正在做什么
还缺什么
什么只是临时方案
接下来准备怎样做
```

这类内容不应该只存在于人的记忆里。

人的记忆不是一个可靠的项目管理系统，尤其是在同时开着多个 Agent 的时候。

## Commit 和文档可以组成完整的追溯链

Git 很擅长记录代码发生了什么变化。

某次 Commit 修改了哪些文件，增加了哪些代码，删除了哪些实现，都可以准确回溯。

但 Commit 通常不擅长完整说明这些变化在整个系统中意味着什么。

例如：

```text
feat: add long-term memory
```

它可能无法回答：

* 这里保存的是事实，还是历史检索经验；
* Memory 能不能直接进入最终回答；
* 当前文件和历史记忆冲突时听谁的；
* 这次实现了哪些层级；
* 哪些功能还没有完成；
* 后续准备怎样扩展。

这些内容不一定适合全部塞进 Commit Message。

更完整的追溯链应该是：

```text
代码
→ 系统实际上怎样运行

测试
→ 当前行为是否符合预期

Commit
→ 这一次修改了什么

文档
→ 为什么这样修改，对系统拓扑产生了什么影响

历史文档
→ 之前为什么不是这样
```

Commit 记录具体变化。

文档记录变化的意义。

把它们放在一起，几个月以后回到项目时，就不需要重新通过代码考古，猜测当初为什么留下这套结构。

你可以知道：

* 做了什么；
* 还没做什么；
* 当时想怎样做；
* 哪些方向被放弃了；
* 哪些东西只是为了给未来留接口。

## 文档拓扑也可以用来选择上下文

Agent 并不是读得越多越好。

把整个仓库、所有历史记录和几十份文档一起塞给它，通常只会制造噪声。

真正有用的是，让 Agent 沿着文档拓扑按需读取。

例如，一个前端任务可能只需要：

```text
docs/README.md
    ↓
docs/architecture/frontend.md
    ↓
docs/design/current-page.md
    ↓
docs/tasks/active/current-task.md
```

一个数据库任务可能需要：

```text
docs/README.md
    ↓
docs/architecture/data-ownership.md
    ↓
docs/architecture/database.md
    ↓
docs/decisions/003-migration-policy.md
```

Agent 从入口文件开始，根据链接进入当前任务真正依赖的文档。

这和代码中的 Import 很像。

使用一个函数时，我们不会把整个项目复制进当前文件。给 Agent 一个任务时，也没有必要让它读取整个项目的全部历史。

好的文档拓扑可以帮助 Agent 用较少的上下文，获得更准确的项目理解。

路径是索引，链接是边，入口文件负责导航。

## 少按几次 Esc

我们经常会在 Agent Thinking 刚出来半句话的时候按下 Esc。

因为它已经表现出要走偏了。

它准备从错误的模块开始，准备重复实现已有能力，或者正在绕过一条本来不应该跨越的边界。

于是我们打断它，再告诉它：

> 这个逻辑属于后端。
> 不要直接访问数据库。
> 那个文件已经过期了。
> 先读一下当前架构。
> 这次不要动另一个模块。
> 这个状态不是前端权威。

同样的话说多了，就应该意识到，它们不应该只存在于聊天记录里。

它们应该进入项目文档。

当 Agent 可以通过文档拓扑提前知道模块关系、权威来源和修改范围时，你需要手动纠正的次数自然会减少。

这不仅是为了让 Agent 做得更好。

它也在给自己节省时间。

没有文档时，每次新任务开始，你都需要重新把整个项目加载进脑子，再用自然语言把它重新解释给 Agent。

文档存在以后，你只需要说明这一次发生了什么变化。

不是每次都从头介绍世界观。

## 文档首先服务的是未来的自己

我们很容易把 `docs/` 理解成一种 Agent 提示词。

文档写得越清楚，Agent 写代码越稳定。

这当然是真的。

但文档首先服务的，其实是未来的自己。

过几个月以后，你同样不会记得所有代码细节。

你可能还记得大概做过一个系统，却不记得：

* 为什么没有选择另一种方案；
* 哪些接口只是临时兼容；
* 哪些模块虽然存在但还没有完成；
* 某项限制是刻意设计，还是当时没时间；
* 下一步原本准备从哪里继续。

如果这些东西只存在于当时的聊天记录和脑子里，它们很快就会消失。

而一套持续更新的文档拓扑，可以让你快速重新进入项目。

它不要求你重新阅读所有代码，只需要沿着文件之间的关系，重新找到项目的主干。

## 文档系统不必很重

把文档说成代码映射和文件拓扑，听起来似乎需要设计一套复杂系统。

其实最开始完全可以很轻。

例如：

```text
docs/
├── README.md
├── architecture.md
├── roadmap.md
└── decisions.md
```

`README.md` 作为入口，告诉人和 Agent 应该从哪里开始。

`architecture.md` 记录模块和依赖。

`roadmap.md` 记录做了什么、还没做什么。

`decisions.md` 记录重要选择和原因。

当文件逐渐变长，再拆成目录。

当决策越来越多，再给它们编号。

当历史方案失效，再建立归档。

文档拓扑不需要一次设计完成。

它可以像代码一样逐渐生长。

唯一重要的是：打开 `docs/` 后，能不能看到项目现在的形状。

## 文档也会产生技术债

文档不是写下以后就自动正确。

目录会迁移，模块会改名，旧链接会失效，某份文档的权威性也可能发生变化。

当文档参与指导 Agent 工作后，错误文档甚至可能比没有文档更危险。

没有文档时，Agent 至少会去读代码。

有一份明确但已经过期的架构文档时，它可能非常认真地按照错误规则实施。

所以，`docs/` 同样需要维护：

* 重构目录时同步更新链接；
* 失效文档移入归档；
* 新文档注明替代了谁；
* 重要文件写清当前状态；
* 代码改变边界时同步更新文档；
* 定期检查路径和重复内容。

文档是代码映射，那么代码发生变化后，映射当然也需要变化。

否则它就只是一张越来越不可信的旧地图。

## 代码让项目运行，文档让项目仍然可被理解

Agent 可以帮助我们写越来越多的代码。

但项目真正容易失去的，不是代码数量，而是开发者对系统结构的理解。

一个优秀的 `docs/` 文件夹，可以是代码的一份低细节映射。

每份文档是节点。

文件路径是索引。

Markdown 链接和引用关系是有向边。

同一套文件可以被看作列表、目录树或有向图，从不同角度表达项目的状态和结构。

它不需要复述代码，却能够保留代码背后的模块拓扑。

它和 Commit 一起形成完整的追溯链：

```text
做了什么
为什么这样做
还没做什么
准备怎样做
```

它让 Agent 少走一些弯路，让你少按几次 Esc。

也让未来的自己，不必一次又一次重新阅读代码、重新理解项目、重新解释整个系统。

代码是项目实际运行的样子。

文档是项目仍然能够被掌握的样子。
