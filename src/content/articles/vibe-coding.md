这篇文章也是用 Vibe 的方式写出来的。

我提供一些破碎的想法、真实经历和还没有整理清楚的判断，AI 负责帮我寻找结构、补齐表达，再由我判断它有没有偏离原意。

就像我平常和 AI 一起写代码一样。

我并不总是先准备一份严密的提纲。很多时候，我只是知道这里有一些值得说的东西，但它们暂时散落在不同的经历里。AI 可以帮助我把这些碎片拼起来，但文章最终想表达什么，哪些内容应该保留，哪些看起来合理却不属于我，仍然需要我决定。

这也是我现在理解的 Vibe Coding。

它不是把整个项目交给 AI，然后在终点接收一个压缩包。它更像是：我逐渐不再关注每一行代码是怎样写出来的，而把注意力移到更高一层——项目要解决什么问题、模块如何连接、边界划在哪里，以及系统是否仍然在沿着我的预期生长。

## 从“这个模块能不能交给 AI”到不再逐行看代码

很早期的 AI 编程，是一个大家还在用 DeepSeek 网页版探讨着“某个模块是否足够独立，能不能交给 AI 完成”的时期。

我们会先把任务切得很小，准备尽可能完整的上下文，把一段代码复制给模型，然后小心地检查它返回的每一行实现。

那时候，AI 更像一个能力很强、但不能完全信任的结对程序员。它能写某个函数、补一个接口、分析一段报错，却很难真正掌握整个项目。

但现在的 Vibe Coding，很多时候已经可以不看代码了。

这里的“不看代码”并不是完全不懂代码，也不是放弃对质量的要求，而是不再把阅读每一行实现作为主要工作方式。

当 Agent 可以自行搜索仓库、读取相关模块、修改多个文件、运行测试、查看报错并继续修复时，开发者的注意力自然会向上移动。

你开始更关心：

* 这个功能应该属于哪个模块；
* 模块之间是否产生了不必要的依赖；
* 数据应该由谁拥有；
* 状态在哪里产生，又在哪里结束；
* 一个改动是否破坏了原来的边界；
* Agent 当前获得的上下文是否足够；
* 测试到底验证了行为，还是只验证了实现；
* 这次修改应该进入哪个分支，怎样被记录和回滚。

以前我们盯着函数和语句，现在更需要盯着项目的拓扑。

## 不需要关注代码细节，不等于只需要想法

Vibe Coding 很适合有想法、但代码实力没有那么强的人。

一个人不需要先完整掌握前端、后端、数据库、部署和测试，才能把自己的想法做成一个可以体验的产品。AI 可以跨过大量传统学习路径中的门槛，让人先接触结果，再逐渐理解背后的结构。

但这并不代表只需要想法就够了。

代码的质量、耦合度、模块边界、数据结构和异常路径不会因为代码由 AI 生成就自动消失。相反，因为 AI 写代码的速度远远快于人类阅读代码的速度，这些问题积累起来也会更快。

你可能只说了一句话：

> 给这个系统增加长期记忆。

Agent 很快就可以生成数据库结构、存储逻辑、检索接口、配置页面和一组测试。但“长期记忆”究竟应该保存什么，是否能直接进入回答，什么时候过期，怎样删除，和当前事实冲突时听谁的，这些都不是代码生成能够自动替你回答的问题。

所以，你只是可以不再关注每一处代码细节了。

你的眼光需要放在更高的位置：项目结构、模块拓扑、信息流向和责任边界。

如果模块之间已经缠在一起，AI 只会更快地继续沿着现有结构添加代码。如果系统没有清晰的事实源，它可能再创造一份新的状态副本。如果测试只追求通过，它也会很自然地修改测试来适配当前实现。

Vibe Coding 比传统编程快得多，但系统最终是否稳定，仍然掌握在开发者手上。

## Just do it

有人问我应该怎样开始 AI 编程时，我经常只回答一句：

> Just do it。

比起先找一套完整课程，背一些提示词技巧，或者研究哪一个 Agent 工具最强，不如先开始做。

Vibe Coding 最好的地方，就是能快速地让你看到 Idea 落地。

虽然它的第一版可能注定是要被重构的一版，但想法快速落地本身就有价值。

它能够让人很快进入一个循环：

```text
产生想法
→ 看到它运行
→ 获得成就感
→ 发现新的问题
→ 实现下一步
```

更重要的是，只有当想法变成一个真实的东西时，你才会知道它是不是真的值得继续。

很多设想在脑子里非常完整，一旦真正使用，就会发现核心需求并不存在；另一些一开始看起来只是小工具的东西，却可能在使用过程中逐渐暴露出更大的空间。

做出来，既是在验证实现，也是在验证 Idea 本身。

## “看到 Thinking 半句话就按 Esc”

我们经常开玩笑地说，有时候看到 AI 的 Thinking 刚出来半句话，就已经开始按 Esc 了。

因为你已经知道它走偏了。

它误解了任务目标，准备修改错误的模块，或者正在用一种看起来很完整、但和项目实际结构完全不合适的方式解决问题。

我觉得这是一种大量 Token 喂出来的习惯。

在不断和 Agent 协作的过程中，人会逐渐形成一种对偏离的敏感度。你未必已经读到它最终生成的代码，但从它准备搜索什么、怎样理解模块关系、选择修改哪些文件，就能判断这次实现是否符合预期。

这种能力很难只通过课程获得。

它需要大量真实任务、错误判断、返工和重构。需要你看到 AI 怎样在上下文不足时自信地补全，怎样把局部最优实现放进错误的位置，也需要看到同一个任务在怎样的描述和项目结构下会得到完全不同的结果。

这也是为什么我会希望刚开始接触 Vibe Coding 的人先 Just do it。

只有实际做过足够多的东西，才能形成对“它正在走偏”的感觉。

## AI 已经是合格的助手，但效率会制造浮躁

现在的 AI 已经是一个合格的助手了。

很多事情都可以直接丢给它：

* 代替搜索引擎寻找资料；
* 帮助处理部署和运维问题；
* 充当翻译器；
* 阅读论文；
* 阅读陌生代码；
* 分析报错；
* 编写测试；
* 整理文档；
* 调查某个技术方案；
* 生成一个可以继续修改的初始实现。

一个人现在能够同时触及的领域，比过去大了很多。

但高效率也会带来另一种问题：浮躁。

当习惯了 Agent 快速输出之后，一旦生成速度变慢、工具链运行时间变长，甚至只是 Token 消耗速度慢下来，焦虑就会上升。

你会开始怀疑它是不是卡住了，会想换一个模型、重新发起任务，或者同时打开另一个 Agent 再做一遍。

我不介意在 Coding Plan 还没有用完的时候，有些浮躁地猛用。

探索期本来就应该允许浪费。多个 Agent 同时尝试、快速推翻某个实现、用大量 Token 换取方向感，这些都有可能是合理的。

但对于已经进入长期维护的项目，浮躁往往意味着比 Token 过期更大的代价。

一个没有想清楚就加入主链的模块，可能在后续产生几十次兼容修改。一次为了赶快通过而做出的边界妥协，可能让之后的每个 Agent 都继续复制这种耦合。一个缺少评估的“优化”，也可能只是让熟悉的问题更容易回答，却破坏了其他场景。

Token 没用完，损失的是套餐。

项目结构失控，损失的是以后每一次修改的成本。

## 从 Vibe 到论文、落地、消融和评估

Vibe 很适合开始，但它不能独自决定什么应该进入最终系统。

我现在更习惯使用这样一套过程：

```text
Vibe
→ 论文与资料
→ 最小落地
→ 消融实验
→ 固定评估
```

Vibe 阶段负责快速把想法做出来。

它不需要一开始就很正确。这个阶段最重要的是获得反馈，观察真实问题在哪里，以及系统的能力上限可能是什么。

当问题逐渐明确后，我会开始读论文、读已有项目、让 AI 帮我搜索资料和比较方案。

论文不是用来照抄架构的。它的作用是告诉我：这个问题还有哪些定义方式，别人尝试过哪些路线，实验是怎样设计的，又有哪些失败结果已经出现。

接下来是最小落地。

不直接把一个方法重度集成进系统，而是先做一个能够被比较的版本。让它在相同数据、相同问题和相同约束下运行。

然后进行消融实验。

把刚刚加入的组件关闭，再运行一次。

如果关闭之后系统没有明显变差，甚至速度更快、结构更简单，那么这个组件可能就不值得留在主链。它也许应该被删除，也许只应该在少数条件下启用。

最后是固定评估。

不再依赖“这几个问题回答得挺好”，而是检查召回、引用、拒答、延迟和稳定性。区分到底是哪一类问题得到提升，又是哪一类发生了退化。

在我的 Search Agent 项目中，Planner、GraphRAG、HNSW 和强推理模型都不是因为看起来先进就默认开启的。

Planner 有作用，但每次调用会显著增加延迟，所以只在证据覆盖不足时启用。

GraphRAG 在关系型问题上表现很好，但不适合普通事实检索，因此被放进低频冷层。

HNSW 的向量检索速度更快，但当前精确检索本身已经不到一毫秒，所以暂时没有必要为了它增加新的复杂度。

这套过程不是为了让 Vibe Coding 变回传统的沉重开发流程，而是为了给高速探索增加一个收敛机制。

Vibe 负责提出可能性。

实验负责决定它有没有资格留下。

## 大项目会逼迫你理解真正的工程问题

Vibe 一个小工具时，很多东西都可以被忽略。

一个脚本只有几百行，模块之间稍微耦合一点没有关系；没有完整文档，也可以重新读一遍代码；分支混乱，大不了重新复制一个目录。

但当项目逐渐变大后，你很自然就会接触到：

* 弱耦合；
* 模块边界；
* 上下文管理；
* 文档编写；
* 文档归档和知识入库；
* 分支管理；
* Git 管理；
* 测试和评估；
* 配置管理；
* 可观测性；
* 版本兼容。

不是因为这些概念听起来专业，而是因为不掌握它们，就很难真正掌握一个大项目，以及与你一起工作的 Agent。

Agent 每次能够看到的上下文是有限的。

如果项目没有文档，它只能反复搜索代码。如果模块没有清晰边界，它很难判断一次修改的影响范围。如果分支和提交记录混乱，它也很难理解某个设计为什么变成今天这样。

过去，文档主要写给其他开发者看。

现在，文档也开始成为 Agent 的长期上下文。

架构说明、模块职责、修改策略、测试方法、兼容边界和失败记录，都会直接影响后续 AI 生成代码的质量。

你怎样组织仓库，某种程度上就是在决定 Agent 怎样理解你的项目。

## 你是项目负责人，而不是代码验收员

我不认为 Vibe Coding 的理想状态，是人类在最后检查 AI 有没有写错语法。

语法、类型、格式、单元测试，应该越来越多地交给工具和 Agent 自己完成。

人的主要职责应该逐渐上移：

* 决定项目真正要解决什么问题；
* 判断一个需求是否值得实现；
* 设计模块关系和能力边界；
* 控制复杂度进入系统的速度；
* 识别 Agent 是否正在偏离；
* 建立能够暴露退化的测试和评估；
* 决定什么应该保留，什么应该删除；
* 对最终系统的稳定性负责。

当你不再逐行阅读代码时，并不意味着责任减少了。

你只是从代码作者，逐渐变成了系统设计者、上下文管理者和项目负责人。

AI 可以替你写大量代码，可以替你搜索、部署、翻译、读论文和排查问题。

但它不会自动替你拥有这个项目。

Vibe Coding 将实现成本降得很低，也因此让错误结构更容易快速膨胀。一个开发者真正需要掌握的，不再只是“怎样把功能写出来”，而是“怎样让一个快速生长的项目仍然属于自己”。

所以，我现在仍然会对刚开始 AI 编程的人说：

> Just do it。

先做出第一个版本，先大量使用，先浪费一些 Token，先感受一次想法真正落地。

然后再逐渐学会看得更高一点。

少看一行代码，多看一个模块；少纠结某个实现细节，多看一次数据流向；少问 AI 能不能写出来，多问这个东西是否应该这样存在。

Vibe Coding 让我们可以不再关注所有代码细节。

但不看代码之后，我们更需要看清整个项目。
